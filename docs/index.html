01 / GETTING STARTED

ALTRUIST
Documentation

A guide to coordinating subjective experiments, configuring tasks, and collecting Quality of Experience data.

Server & clientsExperiment scriptingMeasurement & questionnaires

1.1 What is ALTRUIST?

ALTRUIST is a distributed tool for conducting subjective Quality of Experience (QoE) experiments. It helps researchers coordinate applications, execute experiment procedures, manage test conditions, and collect measurements and questionnaire responses.

An ALTRUIST setup consists of a server application and one or more client containers. The server controls the experiment through a customizable interface and scripts. Each client container contains task agents that perform operations on its device.

COORDINATE

Server application

Run experiment logic, manage conditions, send actions, and receive task feedback.

EXECUTE

Client containers

Run task agents that launch applications, manage files, capture measurements, and display questionnaires.

1.2 How to install ALTRUIST

Use the ALTRUIST application package for your operating system. Keep the executable together with its accompanying files and the Modding directory.

The Modding directory contains experiment scripts, container definitions, questionnaire definitions, and test-condition files. These files determine how your experiment behaves.

Task dependencies

Install additional software on the device where the corresponding task runs.

FunctionRequirement
Packet captureWireshark’s dumpcap tool and a working packet-capture setup
Ping capture on WindowsNping and its packet-capture dependency
Network emulationLinux traffic-control tools
Android device controlAndroid Debug Bridge (ADB)
Application controlThe application being controlled

Running from source

The current source configuration specifies Godot 4.7 .NET and .NET SDK 9. Import project.godot into the compatible Godot editor, build the C# project, and run the main scene.

1.3 How to set up the scripting IDE

ALTRUIST experiment scripts use GDScript. Visual Studio Code with the Godot Tools extension provides syntax highlighting, code completion, error reporting, and navigation.

  1. Install Visual Studio Code and the Godot Tools extension.
  2. Open the ALTRUIST source project folder in VS Code.
  3. Set godotTools.editorPath.godot4 to your Godot executable.
  4. Open the project in Godot, or configure the extension’s headless language server.

To use VS Code as Godot’s script editor, open Editor Settings → Text Editor → External, enable Use External Editor, and set the executable path to VS Code. Use these execution flags:

{project} --goto {file}:{line}:{col}

See the Godot Tools configuration guide ↗.

1.5 How to start ALTRUIST

Use the main menu for interactive startup, or command-line arguments to reuse a launch configuration in shortcuts and automation.

1.5.1 Main Menu new

To start a server, select a server script, choose Standard or Edit mode, and start the server. Standard mode runs the experiment interface. Edit mode opens its configuration interface.

To start a client, select a container script and choose its mode. In Standard mode, enter the server IP address, or leave it empty to use automatic discovery. Edit mode opens the task configuration interface and does not use the server IP address.

The menu also provides controls for creating a client container and opening the questionnaire editor. Previous script selections, modes, and the client IP address are saved and restored when the menu opens again.

1.5.2 Command Line

ArgumentPurpose
-tLaunch type: server, client, or qteditor
-sServer or container script name
-cConfiguration mode: true or false
-ipServer IP address for a client

Example Windows launches:

ALTRUIST_Windows.exe -- -t server -s Exemple
ALTRUIST_Windows.exe -- -t client -s Exemple -ip 192.168.1.10
ALTRUIST_Windows.exe -- -t client -s Exemple -c true
ALTRUIST_Windows.exe -- -t qteditor

Replace Exemple with your script name. The server example selects SS_Exemple_UI.gd and SS_Exemple_Code.gd; the client example selects CT_Exemple_Code.gd.

The -- separator passes the following arguments to ALTRUIST. Command-line startup is handled on desktop platforms.

02 / COORDINATE THE EXPERIMENT

Server Application

Control connected containers through experiment scripts and a customizable interface.

2.1 User Interface

The server interface displays connected containers and the controls defined by the selected server script. Use the connected-container list to check which clients are available before sending actions. The list shows container names and their reported network endpoints.

Experiment controls can include buttons, labels, text fields, and checkboxes. Their meaning depends on the experiment script.

2.1.1 Server Script UI new

Each interface is defined in SS_<name>_UI.gd. Its fetch_ui() function returns the components that ALTRUIST places on the interface.

Components have identifiers so the server code can access them. Buttons can specify a function to call in SS_<name>_Code.gd. For example, a Start button can call a function that launches a program on a connected container.

2.2 Server Script Coding new

Server logic is stored in SS_<name>_Code.gd, which extends ServerScriptAbstract_Code.gd. Use it to define the procedure, respond to interface controls, send actions, and handle task feedback.

When overriding _ready(), call super._ready() to initialize the base script’s test-condition helper.

2.2.1 Send Action to Connected Client

Use SendTask_ConnectedDevices() to send an action. Supply the action, task arguments, optional container names, and optional task names.

func StartPlayer() -> void:
    var task_args := SystemTypes.TaskAgent_Args.new()
    task_args.userID = "Participant01"
    task_args.condition = "A"

    SendTask_ConnectedDevices(
        SystemTypes.Task_Actions.Process_Start,
        task_args,
        ["ParticipantPC"],
        ["Player"]
    )

This targets the task named Player in the container named ParticipantPC. The task and container must exist and be connected.

An empty container list targets all connected containers. An empty task list targets all agents in the selected containers; agents handle the actions relevant to their type.

2.2.2 Receive Action Notification from Client

Client tasks report feedback identifying the action, its result, and a descriptive message. Override OnNotifyMessageReceived() to handle notifications.

func OnNotifyMessageReceived(
    feedback: int,
    action: int,
    details: String
) -> void:
    super.OnNotifyMessageReceived(feedback, action, details)

    if feedback == SystemTypes.Task_Feedbacks.Process_Started:
        print("The application has started.")

Use notifications to track outcomes and decide how the experiment should proceed. Sending an action alone does not confirm that it completed successfully.

2.3 Server Features

2.3.1 Script Loading and Applying Changes new

ALTRUIST loads experiment scripts once during application startup. Changes saved to a script do not affect an application that is already running.

Apply a script change
  1. Edit the script.
  2. Save the file.
  3. Close the ALTRUIST application using that script.
  4. Open the application again.

The updated script is loaded when the application starts.

2.3.2 Server Script UI Editor new

Open a server script in Edit mode to configure its interface. Use Drag Components mode to rearrange controls on the grid and adjust the layout.

Layout changes are automatically saved to the selected server UI script. Button functions are disabled while arranging the interface; their behavior is defined separately in the server code script.

Select Test Matrix to open the condition and test-order tools.

2.3.3 Test Condition Manager new

The Test Condition Manager helps researchers inspect conditions, organize them into testing sets, and generate presentation orders. Open the server in Edit mode and select Test Matrix.

Condition files and parameters

The manager reads condition CSV files associated with the server script, displays recognized files and validation messages, and lists unique condition identifiers. Select an identifier to inspect all matching condition rows.

CD_<name>_netem.csv
CD_<name>_moonlight.csv
CD_<name>_TestOrder.csv

Edit parameter values in the CSV files. Use Reload to read updated files and refresh the displayed conditions.

Creating testing sets

Enter a set identifier and select Create Set. A new set contains the currently loaded condition identifiers.

  • Drag conditions to change their order.
  • Select conditions and use Remove Selected Conditions.
  • Use Add Missing Conditions to restore omitted conditions.
  • Rename or delete a testing set.

Generating presentation orders

ControlResult
Create Set Order from UIOne presentation order per set, following the arrangement shown in the editor
Create Latin Square DesignBalanced Latin-square presentation orders generated independently for each set

Export writes CD_<name>_TestOrder.csv with SetID, OrderID, and condition columns. The experiment script uses these definitions to control its sequence.

NetEM Conditions

NetEM files describe network impairments, including delay, packet loss, and jitter settings. The server script reads the selected condition and supplies the appropriate arguments to a network-emulation task on a Linux container.

A condition definition alone does not change the network. The experiment script must send the action that applies it.

Moonlight Conditions

Moonlight files describe streaming configurations, including frame rate, bitrate, resolution, host address, and additional options. The server script reads these values and uses them in the experiment’s Moonlight launch procedure.

The target container must have Moonlight and the required task configuration.

03 / CONFIGURE THE CLIENT

Client Container Application

Define the operations available on each device and prepare the participant interface.

3.1 User Interface

A client container receives server actions and routes them to its task agents. Its interface displays the configured tasks and the information exposed by each task.

Give tasks meaningful names so the server can target individual operations, especially when several agents share the same type.

Task OS Support Tags new

Task types display operating-system tags indicating declared compatibility. Check these when preparing a container. Overall ALTRUIST platform support and an individual task’s requirements are separate: a task may need an operating system or external tool unavailable on the current device.

3.2 Agent Task Editing

Configure tasks through the Client Container Editor or directly in GDScript. Both methods use the definition stored in CT_<name>_Code.gd.

3.2.1 Client Container Editor new

Select a client container in the main menu and choose Edit mode. To begin with an empty container, use the create-container control and enter a new name.

Configuring task agents

  1. Add a task agent.
  2. Choose its type and check its OS support tags.
  3. Assign a descriptive task name.
  4. Complete the configuration fields for the selected type.
  5. Select Save to write the definition.

Fields can include application paths, command arguments, source and destination directories, network interfaces, measurement settings, and questionnaire selections. The editor provides text fields, checkboxes, file and directory selectors, and dropdowns where appropriate.

You can remove tasks and configure the container’s ADB executable path for Android device control.

Saving and reloading

Save writes the configuration to the container script. The status area reports unsaved changes and the outcome of saving. Reload rebuilds the editor from the saved definition; save changes you want to keep before reloading.

Close and reopen any running client application that needs to use the updated container configuration.

3.2.2 By Coding new

A container script extends ContainerScriptAbstract_Code.gd and returns its definition from get_container_definition().

extends "internal/ContainerScriptAbstract_Code.gd"

func get_container_definition() -> Dictionary:
    return {
        "containerName": "ParticipantPC",
        "showUIOnClientStart": true,
        "adbPath": "PATH",
        "agents": [
            {
                "agent_type": "TerminalCommandTask",
                "taskName": "OpenCalculator",
                "command": "start calc.exe",
            },
        ],
    }

This defines a Windows terminal-command task named OpenCalculator. The server can execute it with ExecuteTerminalCommand. Attribute names must match the fields supported by the task type.

3.3 Questionnaire Editor new

The Questionnaire Editor provides a graphical workspace for creating questionnaires, configuring their appearance, and previewing the participant interface.

Open it from the main menu. Choose Create to start a questionnaire, or select an existing questionnaire and choose Load.

Questionnaire settings

Configure the name, displayed title, font, font size, spacing between questions, question-box color, and text color. Choose portrait or landscape orientation to suit the participant’s device.

Adding and configuring questions

Use Add Question. Each question has a unique identifier, question text, and response type.

Response typeConfiguration
TextboxPlaceholder text and single-line or multiline input
CheckboxResponse options, multiple default selections, and option layout
Radio ButtonsResponse options, one default selection, and option layout
SliderMinimum, maximum, step, default value, and scale labels

Checkbox and radio-button questions provide controls for spacing, alignment, text position, control size, and colors. Slider questions provide controls for the bar and handle appearance, value display, sizing, positioning, and an optional background image.

Live preview

The preview updates as the definition changes. Use it to inspect wording, response controls, spacing, colors, and layout before saving.

Saving and using a questionnaire

Save writes the definition to Modding/Questionnaires/QT_<name>_UI.gd. The editor validates it and reports errors to correct. Load an existing questionnaire before modifying it; creating a questionnaire with an existing filename does not silently replace it.

Select the saved questionnaire in a client container’s QuestionnaireTask configuration. Questionnaire definitions and participant response files are saved separately.

3.4 ADB Manager new

The ADB Manager lets a desktop container discover and manage connected Android devices. Set adbPath to the ADB executable, or use PATH when ADB is available through the system environment.

The interface lists device names, connection types, statuses, and identifiers. It provides controls to refresh devices, enable wireless ADB for an eligible USB-connected device, reconnect a wireless device, and disconnect a wireless connection.

The Android device must be configured for debugging and authorize the desktop connection. Use its device identifier when configuring an Android application task.

04 / EXECUTE & COLLECT

Task Agent Types

Choose the task agents that perform the operations required by your experiment.

Each agent has a name, configuration attributes, and feedback describing the result of an action. The chapter titles describe their functions; container scripts use the exact agent_type names shown below.

4.1 FileTask

FileTask copies or deletes files and directories. Its desktop implementation is FileTask_Desktop, which handles File_Copy and File_Delete.

AttributePurpose
taskNameName used to identify the task
oriFile_NameSource name
oriFile_PathSource directory
destFile_NameDestination name for copying
destFile_PathDestination directory
includeUserConditionIDInclude participant and condition identifiers in the output name
includeDateTimeInclude date and time in the output name
isFolderConfigure a directory operation

Use this task to collect application-generated files or prepare files needed for a test. Check the source path before sending deletion actions.

4.2 ProgramTask

ProgramTask starts or terminates an application using Process_Start and Process_Kill. Use ProcessTask_Desktop for desktop applications or ProcessTask_Android for Android applications controlled from a desktop through ADB.

AttributePurpose
pathToStartApplication launch path
processNameProcess name used for management
argsApplication launch arguments
mainActivityAndroid activity to launch; Android task only
deviceIDTarget Android device; Android task only

Use this task to launch the application being evaluated and close it at the appropriate point in the experiment.

4.3 NetworkTask

NetworkEmulationTask applies network impairments through Linux traffic control. It handles NetEmulation_Start and NetEmulation_Stop.

Set networkInterface to the interface to modify. The start action receives impairment parameters through its task arguments. Use this task with NetEM conditions to introduce controlled delay, loss, or jitter.

The Linux device needs traffic-control tools and sufficient permissions to modify the selected interface.

4.4 TerminalCommand_Task

The terminal-command task uses TerminalCommandTask in container definitions and handles ExecuteTerminalCommand.

Set its command attribute to the operation required by the experiment. Command syntax and available programs depend on the client’s operating system.

4.5 DataCapture_Task

DataCapture_Task provides common configuration for measurement tasks. Add a concrete capture type, such as Wireshark or Ping, to the container. Capture tasks handle DataCapture_Start and DataCapture_Stop.

AttributePurpose
outputPathDirectory for measurement files
outputFileNameBase filename
includeUserConditionIDInclude participant and condition identifiers
includeDateTimeInclude date and time

Feedback includes the output path and capture status. Start capture before the measurement period and stop it afterward.

4.5.1 DataCaptureTask_Wireshark

Capture packets with Wireshark’s dumpcap executable and save them in a .pcap file. In addition to the common capture settings, configure:

AttributePurpose
dumpcapPathExecutable path or name
networkInterfaceInterface to capture
packetLengthMaximum captured packet length; 0 uses dumpcap’s default
captureFilterOptional packet-capture filter

The device needs a working packet-capture installation and permission to capture the interface.

4.5.2 DataCaptureTask_Ping

Record network-response measurements in CSV format, including timestamps, destination address, sequence number, round-trip time, status, jitter, and packet-loss information.

AttributePurpose
destinationIPAddress to measure
packetSizePacket size in bytes
frequencyMeasurement interval in milliseconds
npingPathNping executable path for Windows capture
Measurement interval

Despite its name, frequency is an interval in milliseconds. A value of 1000 represents one second.

4.7 QuestionnaireTask

Questionnaire_Task presents a configured questionnaire, collects participant answers, and saves responses for analysis. It handles Questionnaire_Open, Questionnaire_Save, and Questionnaire_Close.

Attributes

AttributePurpose
questionnaireNameQuestionnaire definition to load
portraitPortrait presentation setting
save_UserIDInclude the participant identifier
save_ConditionIDInclude the condition identifier
save_QTOpenTimeInclude the questionnaire opening time
save_QTSaveTimeInclude the response saving time
save_serverOpenTimeInclude the server’s opening-action timestamp

Saving responses

The saving behavior preserves existing responses:

  • Append: add responses to an existing CSV when its columns match.
  • Create a new file: use a numbered version when the questionnaire’s columns differ from the existing file.
  • Never overwrite: preserve existing response rows during questionnaire saving.

These describe the saving behavior, rather than a three-option selector. Closing without saving discards the current unsaved response. If saving fails, the questionnaire remains open so saving can be retried.
